# spec.md 撰写指南

输入：`00-research/github_top5.md`、`00-research/analysis.md`、`01-spec/sources.md`。
输出：`01-spec/spec.md`。模板见 `assets/spec.md.tpl`。

## 1. 写作原则

1. **需求来自证据，不来自想象**：每条需求至少引用一个 `SRC-`/`OBS-`。竞品共有的功能可作为强证据；竞品缺失但用户明确要求的作为「用户约束」来源（记录用户输入本身为 `OBS-USR-xxx`）。
2. **可验收**：每条需求有可判定的验收标准，禁止「体验好」「响应快」这类无量化形容词。
3. **区分事实与假设**：无来源支撑的推导标 `[假设]`，并指向 `sources.md` 假设段落。
4. **只描述 what，不写 how**：具体实现移到 `plan.md`；spec 中允许写约束（如「必须支持离线」）而非选型（如「用 IndexedDB」）。
5. **范围明确**：每一项「不做」也要有理由或来源。

## 2. 章节顺序

| 章节 | 内容 | 溯源要求 |
| --- | --- | --- |
| 1. 文档元信息 | 版本、日期、输入来源文件、关键词与口径 | 指向 JSON 与 analysis.md |
| 2. 项目目标与背景 | 一句话价值主张、目标用户、问题陈述 | 引用 OBS/SRC |
| 3. 竞品洞察摘要 | Top 5 逐项一句结论 + 共性/差异 | 每项带 SRC |
| 4. 范围 | In scope / Out of scope，各自理由 | Out of scope 需理由 |
| 5. 功能需求 | REQ-FUNC 列表（ID、描述、优先级、来源、验收标准） | 每条 ≥1 SRC/OBS |
| 6. 非功能需求 | 性能、安全、可用性、兼容性、可访问性、合规 | 每条有量化指标与来源 |
| 7. 用户与场景 | 2–4 个 persona / 关键用户旅程 | 可标注假设 |
| 8. 领域模型与术语 | 核心实体、关系、状态机 | 术语引用来源 |
| 9. **板块划分** | MOD 列表（边界、职责、输入/输出、依赖、覆盖的 REQ） | 每个 MOD ≥1 REQ |
| 10. 约束与依赖 | 技术/组织/合规约束 | 标注来源或假设 |
| 11. 风险与开放问题 | 未决问题、验证方式、负责人 | 不得留 TODO 占位符 |
| 12. 来源索引 | 引用到的 SRC/OBS 汇总 | 与 sources.md 一致 |

## 3. 从竞品分析推导需求的方法

对 `analysis.md` 中每个「可借鉴点」执行：

1. 提取能力陈述（如「支持看板拖拽排序」）。
2. 判断是否适用于本项目目标用户；不适用则记入 Out of scope 并说明。
3. 改写为可验收需求：`用户可通过拖拽改变任务状态，变更后 2 秒内持久化并在刷新后保持`。
4. 挂接来源 ID 与验收标准。
5. 生成对应 `TEST-` ID 占位（写入测试矩阵的「关联测试」列），保证需求从出生即可测。

对于用户原始需求中竞品都没有的点，标记为差异化需求，来源是用户输入 `OBS-USR-xxx`，并在风险中记录「无同类实现可参照，需原型验证」。

## 4. 板块划分判据（MOD）

按以下顺序切分，避免过早耦合到技术栈：

1. **按业务能力**：每条独立价值流一个板块（如「账户与权限」「任务领域」「通知」「检索」）。
2. **按变更频率**：易变板块与稳定板块分离。
3. **按数据边界**：拥有独立数据模型/存储边界的候选板块。
4. **按集成边界**：外部系统对接单独成块（支付、第三方登录、消息推送）。
5. 控制粒度：单项目 4–9 个板块为宜；超过 9 个时合并相邻能力。

每个 MOD 必须写清：

```markdown
### MOD-03 通知板块
- 职责：任务状态变更后向订阅者发送站内/邮件通知
- 覆盖需求：[REQ-021, REQ-022]
- 输入：任务领域事件；输出：通知记录与投递状态
- 依赖：MOD-02（任务）、MOD-01（账户与权限）
- 不含：短信与第三方 IM 推送（见 Out of scope）
- 来源：[SRC-GH-002, OBS-014]
```

板块之间依赖必须无环；若有环，在开放问题中记录拆分方案。

## 5. 非功能需求的量化来源

- 优先引用竞品仓库中明确写出的指标（benchmark、SLA、支持平台列表），附 URL。
- 竞品无数据但用户有约束时，来源写用户约束 `OBS-USR-xxx`。
- 两者都没有时，标 `[假设]` 并给出「待基准测试确认」的验证方式；禁止写成已确定事实。

## 6. 与 plan.md 的交接清单

完成 spec 后确认：

- [ ] 所有 REQ 有来源与验收标准
- [ ] 所有 MOD 覆盖 REQ 且无循环依赖
- [ ] 每个 REQ 至少有一个关联 TEST ID（可先占位）
- [ ] Out of scope 与假设均已明确
- [ ] `validate_docs.py` 中 spec 相关检查项通过

不要在此阶段写框架、库、数据库选型；那些属于 `DEC-` 记录在 `plan.md`/`decisions.md`。

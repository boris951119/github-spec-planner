# 多维度交付测试集设计指南

输入：`01-spec/spec.md`（REQ 与验收标准）、`02-plan/plan.md`（阶段与技术栈）、来源台账。
输出：`03-tests/test_suite.md`（人类可读矩阵）与 `03-tests/test_cases.csv`（机器可读用例）。模板见 `assets/test_suite.md.tpl`、`assets/test_cases.csv.tpl`。

## 1. 覆盖维度（每个 REQ 至少覆盖前三类）

| 维度 | 前缀 | 要回答的问题 |
| --- | --- | --- |
| 功能 | `TEST-FUNC` | 验收标准是否满足？ |
| 边界 | `TEST-BND` | 空值、极长、最小/最大、临界数量、并发上限如何？ |
| 异常 | `TEST-ERR` | 网络中断、权限不足、依赖失败、重复提交如何？ |
| 性能 | `TEST-PERF` | 量化指标（p95 延迟、吞吐、资源占用）是否达标？ |
| 安全 | `TEST-SEC` | 越权、注入、密钥泄露、依赖漏洞、会话失效？ |
| 兼容 | `TEST-COMP` | 浏览器/系统/版本/数据迁移/向后兼容？ |
| 数据一致性 | `TEST-DATA` | 并发写入、幂等、事务、刷新后状态、备份恢复？ |
| 可访问性 | `TEST-A11Y` | 键盘可达、语义化、对比度、屏幕阅读器（若 spec 有要求） |
| 回归 | `TEST-REG` | 已修复缺陷与历史行为是否保持？ |
| 验收/交付 | `TEST-ACC` | 发布门禁、回滚、监控告警、文档完整性？ |

不是每个 REQ 都需要全部维度；在矩阵中标注 `N/A + 理由`，不要留空。

## 2. 用例字段与写法

CSV 表头固定：

```
test_id,dimension,related_req,preconditions,steps,expected,source_ids,priority,automated
```

- `related_req`：分号分隔多个 REQ（`REQ-001;REQ-002`），至少 1 个。
- `source_ids`：分号分隔的来源 ID，至少 1 个 SRC 或 OBS。对于纯假设指标，指向 `sources.md` 中的假设条目（用 `OBS-USR-xxx` 或 `SRC-ASSUMPTION-xxx`）。
- `steps`：用中文分号 `；` 分隔，每步可执行、无歧义（写明数据值）。
- `expected`：可判定结果，含具体数值或状态；禁止「正常」「成功」等模糊词。
- `priority`：P0/P1/P2；P0 对应阻塞发布的验收标准。
- `automated`：yes/no；为 no 时需在 `test_suite.md` 说明手工执行方式。

示例行：

```csv
TEST-FUNC-001,功能,REQ-001,已注册用户A已登录,"打开任务页；点击新建任务；输入标题""周报""；点击保存","列表出现标题为""周报""的条目；刷新后仍存在；任务创建时间约为当前时间",SRC-GH-001;OBS-003,P0,yes
```

## 3. 从验收标准生成用例的步骤

1. 读取 REQ 的验收标准，拆出「给定 / 当 / 那么」三元组。
2. 生成 1 条功能用例，逐字对应验收标准。
3. 对标准中的每个变量（数量、长度、权限、状态）生成边界用例，写明具体极值。
4. 对标准中每个外部依赖生成异常用例（超时、错误码、重复请求）。
5. 若标准含量化指标，生成性能用例并写明测量方法与通过阈值。
6. 若涉及写操作，生成数据一致性用例（并发、幂等、刷新保持）。
7. 若 spec 中该 REQ 有安全或合规约束，生成对应用例。
8. 为每条用例回填 `source_ids`（与 REQ 的来源一致，或指向具体假设）。

## 4. 交付测试集的组织

`test_suite.md` 必须包含：

1. 元信息：生成日期、对应 spec/plan 版本、覆盖统计（REQ 总数 / 已覆盖 / 未覆盖及理由）。
2. 维度覆盖矩阵：行=REQ，列=维度，单元格=TEST ID 或 `N/A(理由)`。
3. 用例明细：从 CSV 渲染的表格（可用脚本或手工保持一致）。
4. 执行策略：自动化框架（引用 DEC）、环境要求、测试数据准备、执行顺序。
5. 发布门禁：P0 用例 100% 通过；P1 通过率 ≥ 95%；未通过项需有风险接受记录。
6. 可复用资产：mock 数据、fixture、命令示例（若已有则写路径，若没有写 `[假设]` 与生成方式）。

## 5. 测试来源的诚实性

- 用例的「预期结果」来自 spec 的验收标准，因此来源 ID 可指向该 REQ 的来源；这是合法的间接溯源。
- 若某指标（如 p95 < 300ms）来自假设，必须写 `[假设]` 并在 `sources.md` 登记，不得伪装成竞品数据。
- 不要编造竞品的 benchmark 数值；只引用来源中真实出现的数据。

## 6. 与校验器的配合

生成后运行：

```bash
python3 scripts/validate_docs.py --docs-dir docs --report docs/validation_report.md
```

校验器会检查每条 TEST 是否映射到 REQ、是否有来源 ID、CSV 是否定义完整。失败时优先补齐 `related_req` 与 `source_ids` 列，而不是删除用例。

## 7. 可复用性

- CSV 保持稳定表头，便于导入 TestRail / Jira / 自研平台。
- `test_id` 一旦发布不复用、不重命名；需求变更时新增用例或在矩阵中标注废弃原因。
- 保留生成它的 spec 版本号，便于回溯「当时依据哪版需求」。

# plan.md 撰写指南

输入：`01-spec/spec.md`（REQ / MOD / 验收标准）、`00-research/analysis.md`（竞品技术栈证据）、`01-spec/sources.md`。
输出：`02-plan/plan.md` 与 `02-plan/decisions.md`。模板见 `assets/plan.md.tpl`。

## 1. 核心约束

- **技术栈不能凭偏好写**：每个选型必须有 `DEC-XXX`，含依据（SRC/OBS）、至少两个备选方案、取舍代价。
- **任务必须回溯到板块或需求**：每个 `TASK-XXX` 写明覆盖的 `MOD-`/`REQ-`，以及完成定义（DoD）。
- **估算标注依据**：人日估算若来自团队约定写 `OBS-USR-xxx`；否则标 `[假设]` 并说明校准方式。
- **不写占位符**：用具体数值或「待原型验证 + 验证方法」替代 TODO/TBD。

## 2. decisions.md：技术栈决策记录

每个决策按 `DEC-` 卡片书写：

```markdown
### DEC-001 后端语言与框架
- 决策：TypeScript + Node.js 22 + Fastify
- 依据：[SRC-GH-002, OBS-009]（Top 5 中 3 个使用 Node/TS；本团队 TS 经验见 OBS-USR-002）
- 备选方案：
  - Go + Gin [SRC-GH-004]：性能更好但团队经验不足
  - Python + FastAPI [SRC-GH-005]：数据生态好，但并发模型不匹配 REQ-014
- 代价：需引入编译步骤与类型治理
- 影响板块：MOD-02, MOD-04
- 影响任务：TASK-003, TASK-007
```

必须覆盖的选型维度（按项目实际裁剪，未选的写「不适用 + 理由」）：

| 层级 | 典型决策 |
| --- | --- |
| 前端 | 框架、构建工具、状态管理、样式方案、组件库 |
| 后端 | 语言、框架、API 风格（REST/GraphQL/gRPC）、认证方式 |
| 数据 | 主存储、缓存、搜索、文件存储；迁移与备份策略 |
| 基础设施 | 部署形态、容器/无服务器、CI/CD、环境划分 |
| 质量 | 单测/集成/E2E 框架、mock 策略、覆盖率门槛 |
| 可观测 | 日志、指标、链路追踪、告警 |
| 安全合规 | 依赖扫描、密钥管理、许可证合规（由 SRC 的 license 字段支撑） |

依据不足时：明确写「竞品未提供该维度证据，依据为团队约束 OBS-USR-xxx / 假设」。不得伪造竞品技术栈。

## 3. plan.md：执行计划结构

```markdown
# 执行计划
## 1. 输入与依据（spec.md 版本、来源文件、生成日期）
## 2. 技术栈总览（表：层级 / 选型 / DEC ID / 来源）
## 3. 阶段划分
| 阶段 | 目标 | 覆盖板块 | 任务 | 出口条件 | 人日 | 风险 |
## 4. 任务明细
### TASK-001 ...
- 覆盖：[MOD-01, REQ-001]
- 产出：...
- DoD：...（可验证）
- 依赖任务：TASK-xxx
- 估算：2 人日 [假设/依据]
- 验证方式：TEST-xxx
## 5. 依赖关系与关键路径
## 6. 里程碑与验收门禁
## 7. 风险与缓解
## 8. 与测试集的对应表（REQ → TEST → 阶段）
## 9. 复现与审计（调研脚本命令、校验命令）
```

## 4. 阶段划分建议

1. **阶段 0：验证与骨架** —— 原型验证高风险假设、搭建仓库/CI/环境、锁定 DEC。
2. **阶段 1：核心领域** —— 承载主价值流的 MOD，先打通端到端最小闭环。
3. **阶段 2：支撑能力** —— 权限、通知、检索等横向板块。
4. **阶段 3：质量与交付** —— 性能、安全、兼容性、可访问性，执行完整测试集。
5. **阶段 4：发布与回滚演练** —— 部署、监控、回滚、文档。

阶段出口条件必须用可判定语言，如「TEST-CORE-001~012 全部通过，P0 需求验收标准 100% 满足」。

## 5. 从 spec 到任务的映射规则

- 一个 MOD 至少拆成一个 TASK；复杂 MOD 按「数据模型 → 接口 → 界面 → 集成」拆。
- 每个 TASK 的 DoD 必须引用至少一个 TEST ID；若测试集尚未生成，先在 plan 中登记 TEST ID，再由测试生成阶段补全内容。
- 横向关注点（认证、日志、错误码）单独成 TASK，避免散落在每个业务任务里无法验收。
- 依赖按 MOD 依赖图展开；出现环时回到 spec 修订边界，不要在 plan 中打补丁。

## 6. 常见错误

- 把「采用微服务」当依据，没有 SRC/OBS 支撑 → 改为 DEC 并补备选与代价。
- 直接复制竞品技术栈但未验证许可证兼容 → 引用 SRC 的 license 字段，风险中记录。
- 任务只写「实现登录」没有 DoD 与验证方式 → 补 DoD 与 TEST ID。
- 人日估算无依据且写成确定值 → 标 `[假设]` 并写校准方法（如首个迭代后重估）。
